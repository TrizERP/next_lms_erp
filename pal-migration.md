Migrating the LMS **PAL** module (menus: "PAL" ENTRY + "PAL Report" REPORT) from the Laravel ERP (`C:\Users\MILAN\Downloads\next_lms_erp`) into the Next.js frontend (`C:\Users\MILAN\Downloads\lms_k12`), under `app/pal/`.

Non-obvious facts (source of truth = Laravel):
- **The legacy student PAL UI uses `/lms/*` web routes** (`palController`), NOT the V4 `/api/pal/*` engine. Keep them distinct.
- **PAL V4 API (`/api/pal/*`, 31 routes → `PALAPIController`)** is now integrated as a separate `app/pal/intelligence` dashboard + `app/pal/data/pal-v4.ts`. The 27 `pal_*` tables EXIST in the live DB (`vivek_erp`) but are sparsely populated; the engine logic works (verified via tinker). It was 500-ing on live due to a **namespace/case bug**: dir `app/Http/Controllers/api/PAL/` (lowercase `api`) vs declared `namespace App\Http\Controllers\Api\PAL` (capital `Api`) — fatal on Linux. **Fixed** (uncommitted): namespace + the `use` in `routes/pal_api.php` → lowercase `api`. Deploy needs `php artisan route:clear` if cached. Envelope is `{success,data}`; `getMasteryMap` returns 3 keys with a **literal leading space** (` mastered_concepts` etc.).
- **PAL V4 auth + tenant scoping (DONE, uncommitted):** the `api/pal/*` group is now secured by route middleware `pal.auth` (`app/Http/Middleware/PalApiAuth.php`, registered in `Kernel::$routeMiddleware`, applied in `routes/pal_api.php` via `->middleware('pal.auth')`). It requires the GenTux JWT (frontend already sends `Authorization: Bearer <user_token>`), decodes the payload (`id`/`sub_institute_id`/`is_admin`/`is_student`/`client_id`/`user_profile_id`) into a `pal_auth` request attribute, and enforces per-learner ownership. **Key fact: the `pal_*` tables have NO `sub_institute_id` column** (`learner_id` = user id directly), so tenant is resolved by joining learner_id → `tblstudent`/`tbluser`.`sub_institute_id`. Rules: student → own learner id only; staff/institute-admin → learner must be in caller's institute (CSV membership supported); client-admin (sub_institute_id 0 + client_id) → scope by `school_setup.client_id`; `is_admin===2` super-admin → unrestricted. Target learner resolved from route `{learnerId}`, body `learner_id`, or (session-only routes) `pal_learning_sessions.learner_id` via `{sessionId}`. `teacher-insights` additionally role-gated (students 403) in the controller. Denials are `{success:false,message}` 401/403; frontend `fetchV4Data` maps these to clear messages. GenTux JWT uses `getenv('JWT_SECRET')` HS256 (same secret as login); payload built in `ApiLoginController::login`.
- **`/lms/*` PAL GET endpoints return JSON when `type=API`** via the `is_mobile()` helper (`app/Helpers/Helper.php`), which also renames `status_code`→`status` (uppercased). Applies to `index`, `create`, `show`, `misconception`, `pedagogy-suggested-content`, `palreport`.
- **Backend gap — quiz submit `store()` (`POST /lms/pal`)**: it does NOT honor `type=API`; it always `redirect()`s to `pal.show`. A browser SPA can't read the cross-origin 302 Location. Solved WITHOUT backend change via a Next BFF proxy `app/api/pal/submit/route.ts` (server-side POST with `redirect:'manual'`, parse Location for `questionPaperId` + `online_exam_id`). Recommended backend cleanup: make `store()` branch on `type=='API'` and return JSON.
- **`SessionMiddleware` does NOT hydrate session from the Bearer token** (for `type=API` it just passes through). So endpoints that read tenant/user from `session()` only are broken for the token SPA. **Backend edits made (uncommitted, in next_lms_erp, request-with-session-fallback so web/Blade is unchanged):** `palController::show/misconception/generateMisconceptionContent` now read `user_id`/`sub_institute_id`/`syear` from the request; `assessmentQuestionController::generateAdaptivePractice/submitPractice/getPracticeHistory/getSpacedRepetition` now read `sub_institute_id` from the request. Pattern used: `$request->get('x') ?: session()->get('x')`.
- **CSRF**: `VerifyCsrfToken::$except` includes full-host globs `https://erp.triz.co.in/*` and `https://dev.triz.co.in/*`, so SPA POSTs to those hosts are CSRF-exempt (submit-practice, personalize marks work with direct client POST).
- **Nav**: PAL menu is backend-driven; frontend mapping added in `app/data/routeMapper.ts` (`pal.index`→`/pal`, `palreport.index`→`/pal/report`, `result_personalize_marks.index`→`/pal/personalize-marks`).
- PAL stores chapter id in `question_paper.paper_desc`; `exam_type='PAL'`. Levels: `<40 easy`, `40-<70 medium`, `>=70 hard`. First attempt = mixed easy4/med3/hard3; later attempts promote one level.
- Frontend data layer: `app/pal/data/pal.ts` (uses `lib/erp-client.ts` `buildSessionContext`/`appendCommonParams`/`createAuthHeaders`). Report exports via `lib/table-export.ts`.

**syear gotcha (fixed in `lib/erp-client.ts` `buildSessionContext`):** PAL data is filtered by `question_paper.syear`. The correct "current" year = the **active academic term** (`login.academicTerms[0].syear`, the term whose date range covers today) — this is what the Laravel session uses. The frontend was falling back to `academicYears[0].syear` (earliest year on file, usually empty) and blindly trusting `localStorage.selectedAcademicYear` (which can be a stale/wrong-format value like `"2024-2025"` → normalized to `2024`), so PAL Report showed 0 rows. Fix: prefer the active-term year, and only honor `selectedAcademicYear` when it matches one of the session's real years. Verified on dev (`lms@triz.co.in`/admin, sub_institute 1): PAL data lives in syear **2021 (16 rows)** and **2022 (2 rows, the active year)**; 2020/2023-2026 are empty. NOTE: the **PAL ENTRY landing is empty for admin/non-student logins by design** (`palController@index` → `getStudents([user_id])` returns nothing for a non-student) — same in the old Blade UI; only the PAL **Report** shows institute-wide data for admins. `app/course-master/page.tsx` `getSyear()` has the same latent `academicYears[0]` weakness (not yet changed; H5P/course-master were not reported broken).

**Landing subjects were always empty in the SPA (fixed):** `palController@index` builds `subjectList` via `AJAXController@getSubjectList`, which reads `sub_institute_id` from **session only** → empty for every `type=API` call (all SPA calls), so the PAL landing showed "No PAL subjects found" for students too, not just admins. Fix (frontend, no backend change): source subjects+chapters from **`POST /api/lms-courses`** (institute-wide catalog, `lms_subject` grouped by category, each subject has a `chapters[]`; ~1.3MB so cached per session in `app/pal/data/pal-lookups.ts`), filtered by the learner's `standard_id`. Attempts (`/lms/pal` `attemptExams`) carry `subject_id` + `paper_desc`(chapter_id); any attempted chapter missing from the catalog is appended as "Chapter #id" so history is never lost.

**Admin/teacher student picker (added):** non-student profiles (e.g. `lms@triz.co.in` = "LMS Teacher") get a Grade→Standard→Division→Student picker on `/pal` and view any student's PAL.
